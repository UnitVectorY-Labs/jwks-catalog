Welcome to the JWKS Catalog

The JWKS Catalog is a centralized, open resource designed for developers and security professionals to easily locate, compare, and evaluate public JSON Web Key Set (JWKS) endpoints from popular services. This site aggregates key endpoints from well-known providers to simplify the discovery of cryptographic keys used in modern authentication systems.

Catalog Purpose

  • Simplification and Comparison: Quickly find and compare the implementation of JWKS endpoints across different providers.
  • Reference and Research: Use this catalog to understand how various popular services implement token validation and key distribution.
  • Community Driven: Contributions are welcome! Add or update entries for any public-facing, popular sites by submitting the relevant JWKS and OIDC configuration endpoints on GitHub.

Understanding the Endpoints

This catalog features three types of endpoints:

OpenID Connect (OIDC) Endpoints
OIDC endpoints provide configuration information as defined in the OpenID Connect Discovery 1.0 specification. They are served at the standard path /.well-known/openid-configuration and offer a discovery mechanism for client applications to obtain necessary configuration data for authentication.
Note: Not all services expose an OIDC configuration endpoint. Some instead expose OAuth 2.0 authorization-server metadata, or only a JWKS endpoint.
OAuth 2.0 Authorization Server Metadata Endpoints
OAuth 2.0 authorization server metadata endpoints, standardized in RFC 8414, are served at the standard path /.well-known/oauth-authorization-server and publish authorization-server configuration such as authorization, token, and (when available) JWKS endpoints. They provide OAuth 2.0 discovery independently of OpenID Connect.
JWKS Endpoints
JSON Web Key Set endpoints, standardized in RFC 7517, allow clients to retrieve public keys used to verify the signatures of tokens (such as JWTs). These keys are critical for ensuring token integrity and authenticity.

Identity provider signals

The catalog looks for distinctive response headers in crawled OIDC, OAuth metadata, and JWKS endpoints. The filter and service pages show matches for:

Provider signalResponse headerEvidence source
OktaX-Okta-Request-IdOkta request debugging
Auth0X-Auth0-L, X-Auth0-RequestIdAuth0 discovery response
SalesforceX-Sfdc-Edge-Cache, X-Sfdc-Request-IdObserver header notes
ForgeRock / PingX-ForgeRock-TransactionIdPing request tracing

These are best-effort hints, not verified ownership. Salesforce headers identify its edge infrastructure, which also serves non-identity products; they do not establish that Salesforce provides the identity service. Proxies can add or remove headers, and a service shown as Other may still use one of these providers. A service can show more than one signal.
